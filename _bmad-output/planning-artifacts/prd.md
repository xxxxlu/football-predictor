# Product Requirements Document - football-predictor

**Author:** xiaolu
**Date:** 2026-07-13

## Executive Summary

`football-predictor` 是一个面向 3～10 人朋友群的免费足球判断账本 PWA。它解决群聊与表格无法自动维护赛程、赔率、积分和排名的问题，同时避免传统真钱盘口产品的充值、提现、资金托管与现金结算模式。

用户注册或登录后，可以创建公开或私人房间：公开房间出现在公开大厅，任意已登录用户确认规则后可直接加入；私人房间通过不可枚举邀请链接加入。每个房间拥有独立的持久积分账户；用户根据确认赔率填写虚拟积分投入，系统负责赔率校验、积分冻结、自动封盘、赛果结算和排行榜更新。每一笔积分变化都能追溯到预测单、赔率快照和账本记录，房主无需人工开盘或计算结果。

产品采用分阶段交付：

- **世界杯验证轨：** 注册登录、用户创建公开或私人房间、公开大厅发现与加入、一个目标验证房间、单一 bookmaker、赛前胜平负、单项预测、自动结算与房间榜；滚球数据只展示。
- **正式产品轨：** 扩展公开大厅、完整多房间管理、亚洲让球、大小球、串关、可靠滚球预测、补分流程和长期战绩。

产品始终保持非现金边界：无充值、提现、兑换、奖品或积分交易；全站固定展示禁止真钱活动声明，平台不处理、认可或结算用户在站外自行形成的金钱往来。

### What Makes This Special

- **足球判断账本，而非普通比分游戏：** 赔率和虚拟投入共同表达判断信心。
- **免费娱乐，而非真钱盘口：** 积分没有货币价值，产品能力不包含任何资金链路。
- **房间自动运行：** 分享链接即可开始，数据同步、封盘和结算无需房主维护。
- **结果可以解释：** 用户可以追溯确认赔率、冻结积分、结算规则和排名变化。
- **数据成本受控：** API-FOOTBALL 免费档内部硬限制为 95 次/日，所有用户共享服务器缓存。
- **验证代码可持续演进：** 世界杯验证轨与正式产品共用 Provider Adapter、赔率快照和积分账本模型，不建立一次性实现。

## Project Classification

- **Project Type：** `web_app`（H5/PWA + 后端 API + 定时同步任务）
- **Domain：** `sports_data_social_prediction`
- **Complexity：** `medium`
- **Project Context：** `greenfield`
- **Primary Users：** 注册用户、房主与两个预置超级管理员
- **Core External Dependency：** API-FOOTBALL 赛程、赔率、比分及赛果数据

## Success Criteria

### User Success

- 用户从打开有效邀请链接到加入房间的中位时间不超过 30 秒。
- 用户加入房间到提交首张有效预测单的中位时间不超过 60 秒。
- 至少完成 1 个私人房间、3～10 名参与者、连续 3 场目标比赛的验证。
- 至少 60% 已加入成员在 3 场目标比赛中的至少 2 场提交预测。
- 至少访谈 4 名参与者，确认其能够理解确认赔率、可用与冻结积分、预测结果、积分变化和房间排行榜。
- 封盘前其他成员无法看到具体预测；封盘后可以复盘已公开选择。
- 比赛结束后，用户无需房主解释即可理解系统结算结果。

### Business Success

本项目不设置收入、付费转化或大众用户规模目标。

- 世界杯验证结束后，原房间继续参与至少一个俱乐部赛事。
- 原房间在后续赛事中连续完成至少 3 场比赛的预测与结算。
- 房主无需手工录入赛果、修改赔率或计算积分。
- 产品在免费 API 请求额度内持续运行，不因用户页面操作增加供应商成本。
- 所有页面持续保持无充值、提现、兑换、奖品或真钱活动的产品边界。

### Technical Success

- API-FOOTBALL 每日计费请求不超过 95，官方 100 次配额不得耗尽。
- 所有用户读取服务器缓存；刷新页面、切换房间和重复打开比赛不得触发供应商请求。
- 赛前盘口在 `OPEN`、实际开球前且赔率快照未超过新鲜度阈值时允许提交，不设置人为提前截止时间。
- 数据源提前封盘时立即禁止提交；数据源未及时封盘时，系统在实际开球时间强制关闭赛前盘。
- 封盘或实际开球后被接受的赛前预测单数量为 0。
- 提交与封盘并发时返回 `MARKET_CLOSED`，不创建预测单、不冻结积分。
- 重复提交导致的重复预测单或重复冻结积分数量为 0。
- 已结算预测中无法由账本解释的积分差异数量为 0。
- 供应商最终赛果确认后，自动结算经重试成功率达到 100%。
- 每张预测单保存不可变赔率快照、bookmaker、供应商时间、服务端接收时间和原始数据哈希。
- 数据源不可用、过期或额度不足时自动暂停预测，不使用旧赔率兜底。
- 全站固定显示非现金声明；首次加入和创建房间时记录规则版本与确认时间。
- 账户恢复成功后，旧恢复码和既有会话继续有效的数量为 0；新恢复码仅在恢复完成页展示一次。
- 邀请链接重置后，旧链接成功加入房间的数量为 0，因链接重置而被移除的既有成员数量为 0。
- 相同预测单、结算版本和操作类型重复执行时，新增账本流水和余额变化数量均为 0。
- 最坏比赛日回放中，静态、赛前、滚球与结算请求总数不超过 95，普通同步消耗受保护 10 次结算额度的次数为 0。

## Product Scope

### Authoritative Scope Decisions

- 本 PRD 是身份模型与阶段范围的当前批准基线；与输入 Product Brief 或 Journey Blueprint 冲突时，以本节、Functional Requirements 和 Non-Functional Requirements 为准。
- Phase 1 使用用户名和密码注册登录，并提供单次使用的恢复码；不采用“仅昵称 + 浏览器本地身份”作为账户模型。
- Phase 1 允许用户自助创建和加入多个公开或私人房间；公开大厅只负责发现 `ACTIVE + PUBLIC` 房间，世界杯验证验收仍只要求运行一个 3～10 人目标房间。
- Phase 2 再开放补分、高级盘口、串关、可靠滚球积分预测、市场共识和模型赔率。
- Phase 3 聚焦跨赛事延续、长期统计和历史荣誉，不改变免费、非现金与自动运行边界。

### Phase 1 — 世界杯验证 MVP

- 普通用户使用用户名和密码注册、登录，并获得一次性恢复码。
- 用户设置展示昵称，自助创建公开或私人房间；公开房间从大厅直接加入，私人房间通过邀请链接加入。
- 系统支持用户加入多个房间；正式验证聚焦一个 3～10 人目标房间。
- 两个预置超级管理员通过统一入口登录并使用角色页面，不建设独立后台。
- 单一 bookmaker 的世界杯赛前胜平负与单项虚拟积分预测。
- 每房间独立持久积分账户、赔率快照、积分冻结和不可变账本。
- 封盘前允许提交；盘口关闭、实际开球或数据过期后由服务端强制拒绝。
- 自动赛果结算、房间排行榜、预测历史和账本明细。
- 滚球比分与赔率只读展示。
- API-FOOTBALL 每日请求硬上限 95 次。
- 固定非现金声明、规则确认、举报和最小超级管理员处置能力。

### Phase 2 — 正式产品

- 公开排行榜和更完整的多房间管理。
- 房间补分申请与 `OWNER_GRANT`；不再使用单一系统公开房间或 `SYSTEM_GRANT` 模型。
- 高级房间档位（`STANDARD`/`ADVANCED`）与正确比分（Correct Score）平台虚拟盘，作为首个交付的高级盘口增量。
- 亚洲让球、大小球、2～8 项串关及数据可靠后的滚球积分预测。
- 多 bookmaker 市场共识与明确标识的模型赔率。
- 阶段榜、长期战绩和赛后分享卡。
- 正式公开前完成体育数据展示授权检查。

### Phase 3 — 长期扩展

- 房间跨世界杯、英超、欧冠及其他足球赛事长期存在。
- 用户沉淀命中率、虚拟收益率、擅长盘口和历史荣誉。
- 形成“提交预测 → 封盘公开 → 自动结算 → 分享战报 → 下一轮”的朋友观赛循环。
- 在完全免费、非现金和无需房主手工维护的边界内提高赛事覆盖、数据实时性与复盘能力。

### Out of Scope — 全阶段排除

- 充值、提现、支付、资金托管、真钱结算、现金或实物奖励、积分购买、转让、交易或兑换。
- 手机号、短信验证码、邮箱验证码或社交账号登录。
- 独立管理后台、人工开盘、人工修盘、人工覆盖余额或人工结算。
- 原生 Android/iOS 应用、聊天、私信、评论及复杂社区功能。
- 广告、会员收费、多租户白标 SaaS、代理、抽成或输赢分成。
- 抓取外围网站、导流第三方下注平台或提供外部下注入口。
- 未完成数据覆盖、新鲜度、结算回放及授权检查的盘口积分预测。

## User Journeys

### Journey 1：阿凯第一次参加朋友预测局

**Opening Scene**

阿凯在微信群里收到朋友发来的世界杯房间链接。以前大家只是在群里发比分看法，赛后没人记得谁猜得准，也经常因为计算方式不同产生争论。

**Rising Action**

阿凯打开链接，看到房间名称、房主昵称和“仅供娱乐、无充值提现、积分不可兑换”的提示。他注册或登录账户、设置展示昵称并确认规则后加入房间，系统为他创建该房间独立的 10,000 分账户。

注册完成页只展示一次恢复码并要求阿凯确认已保存。以后如果忘记密码，他可以在新设备提交用户名、恢复码和新密码；恢复成功后旧恢复码与全部旧会话失效，系统再展示一次新的恢复码。恢复码遗失时只能创建新账户，系统不合并旧账户积分或房间身份。

房间首页展示即将开始的比赛。阿凯进入比赛详情，看到单一 bookmaker 的赛前胜平负赔率。他选择一个结果，输入 1,000 分，页面显示确认赔率和预计返还。

**Climax**

阿凯提交预测。服务端再次确认盘口仍为 `OPEN`、比赛尚未开球、赔率快照仍然有效，并在同一事务中冻结 1,000 分、生成预测单和赔率快照。

比赛封盘前，其他成员只能看到阿凯“已提交”，不能看到他的选择。封盘后，大家的预测自动公开。

**Resolution**

比赛结束后，系统自动读取最终赛果并完成结算。阿凯看到余额、净收益、预测详情和房间排名，无需房主解释计算过程。

**揭示的能力**

- 邀请链接与房间加入
- 账户注册、登录与展示昵称
- 单次恢复码保存、账户恢复和旧会话失效
- 独立房间积分账户
- 赛事、盘口和赔率展示
- 单项预测与积分冻结
- 封盘前隐藏、封盘后公开
- 自动结算、账本和排行榜

### Journey 2：小林在封盘瞬间提交

**Opening Scene**

小林在比赛开球前最后一分钟才决定预测。页面仍显示之前加载的赔率，但数据源刚刚暂停盘口。

**Rising Action**

小林输入积分并点击提交。前端请求携带赔率快照版本和幂等键，但不自行决定是否接受。

**Climax**

服务端检查发现盘口已经 `CLOSED`，或当前时间已经达到实际开球时间，因此返回 `MARKET_CLOSED`。系统不创建预测单，也不冻结任何积分。

另一种情况下，如果盘口仍开放但赔率发生变化，系统返回 `ODDS_CHANGED` 和最新赔率，让小林重新确认，而不是使用旧赔率提交。

如果供应商数据已经超过新鲜度阈值，系统将盘口标记为暂不可用，不使用缓存旧赔率兜底。

**Resolution**

小林看到明确提示和未变化的积分余额。他理解预测失败是因为封盘，而不是系统扣分异常。

**揭示的能力**

- 服务端最终封盘校验
- 实际开球时间兜底封盘
- 赔率版本校验
- 幂等提交
- 数据新鲜度检查
- 拒绝提交时不产生任何账本变化
- 清晰的错误原因与恢复动作

### Journey 3：老周创建并维持朋友房间

**Opening Scene**

老周负责组织朋友看球。过去他需要创建表格、催大家填写、赛后查比分并手工算分，几场后就不愿继续维护。

**Rising Action**

老周创建房间时确认使用规则：房间不得用于任何真钱活动，平台不处理站外资金约定。他生成邀请链接并分享到微信群。

成员通过链接登录或注册后，确认当前规则版本并自行加入；重复打开同一链接不会重复创建成员关系或发放初始积分。老周可以看到成员数量和谁已经提交，但封盘前不能查看具体选择。

如果邀请链接泄露，老周可以重置链接。旧链接立即失效，已加入成员、积分账户和预测记录保持不变；关闭或受限房间拒绝新成员加入。

**Climax**

比赛结束后，系统自动完成赛果同步、积分结算和排名更新。老周不需要录入赛果或修改积分。

正式产品阶段，如果成员积分耗尽，可以向老周发起补分申请；老周填写数量并批准。补分记录为 `OWNER_GRANT`，增加可用余额但不计入预测收益。

**Resolution**

世界杯结束后，老周保留原房间和成员，直接切换到俱乐部赛事继续参与，无需重新建群或迁移成绩。

**揭示的能力**

- 创建房间与规则确认
- 邀请链接生成和重置
- 加入规则确认、幂等加入和旧链接失效
- 成员列表与提交状态
- 自动赛事与结算流程
- 房间长期存在
- 正式阶段的补分申请、审批和审计
- 禁止真钱用途与关闭违规房间的能力

### Journey 4：超级管理员处理数据源异常

**Opening Scene**

一场目标比赛即将开始，API-FOOTBALL 当日请求已接近内部 95 次上限，部分赔率响应发生延迟。

**Rising Action**

调度器读取供应商响应头与本地计数，发现剩余额度接近受保护的 10 次结算预算。系统先停止滚球展示同步，再停止普通赛前赔率同步，保留最终赛果、结算和失败重试请求。

受影响的盘口因数据过期自动进入 `DATA_UNAVAILABLE`，用户只能查看比赛，不能继续提交预测。

**Climax**

比赛结束后，结算任务获取最终状态并执行幂等结算。如果供应商稍后更正赛果，系统逆向原结算、写入更正账本并重新计算排名，而不是直接覆盖历史记录。

超级管理员通过日志和健康状态确认：

- 当日请求未超过 95
- 没有过期盘口被接受
- 没有重复结算
- 每笔更正都能追溯到供应商数据

### Technical Constraints

- 所有积分变化必须写入不可篡改的账本流水，不允许直接覆盖余额。
- 预测单必须保存赔率快照、盘口状态、供应商数据时间、服务器提交时间和结算版本。
- 积分冻结、结算、退款、补分与赛果更正必须幂等；更正通过冲正流水和重新结算完成，不删除或覆盖原始记录。
- 服务器是封盘判断的唯一权威：盘口不是 `OPEN`、实际时间已到开球时间或赔率快照过期时均不得接受预测。
- 提交与封盘发生竞争时返回 `MARKET_CLOSED`，不得创建预测单或冻结积分。
- API 异常或赔率新鲜度无法确认时，盘口进入 `DATA_UNAVAILABLE`；系统宁可暂停预测，也不得接受无法验证的赔率。
- API Key 仅保存在服务端；所有用户共享服务器缓存，客户端行为不得直接触发供应商请求。
- API-FOOTBALL 日请求内部硬上限为 95 次，并优先保护最终赛果、结算和重试预算。
- 房间访问、房主操作、系统补分和赛果更正必须进入审计日志；恢复凭证必须以不可逆摘要保存。

### Point & Settlement Contract

**账户字段：**

- `available_points`：当前可投入积分，始终不小于 0。
- `frozen_points`：已提交但尚未最终结算的投入，始终不小于 0。
- `correction_debt`：赛果更正需要扣回、但当前可用积分不足时的待抵扣额，始终不小于 0；它不是可用积分，也不改变其他未结算预测的冻结额。
- 用户可投入金额仅由 `available_points` 决定；存在 `correction_debt` 时，后续预测返还或补分先抵扣债务，剩余部分才进入 `available_points`。

设投入为 `S`、确认 decimal odds 为 `O`。接受预测时必须原子执行 `available_points -= S`、`frozen_points += S` 并写入冻结流水。

| 最终结果 | 积分处理 | 预测净收益 |
|---|---|---:|
| 赢 | `frozen_points -= S`；返还 `R = round_half_up(S × O)`，先抵扣 `correction_debt`，余额进入 `available_points` | `R - S` |
| 输 | `frozen_points -= S`；不返还积分 | `-S` |
| 走盘 | `frozen_points -= S`；返还 `S`，先抵扣 `correction_debt` | `0` |
| 确认取消/无效 | `frozen_points -= S`；返还 `S`，不计入预测输赢 | `0` |
| 推迟/中断/状态未最终确认 | 保持冻结和待结算，不创建结算流水 | 未确定 |

- 所有积分以整数记录；只在预测单最终返还值上执行一次四舍五入，禁止逐步重复舍入。
- 赛果更正必须先按原结算版本写入等额反向流水，再按新结算版本结算；原流水不可修改或删除。
- 冲正扣减超过当前 `available_points` 时，可用积分降至 0，差额写入 `correction_debt`；排行榜与预测净收益立即按更正后结果重算。
- 冻结、结算、取消退款和更正操作的幂等作用域为“预测单 + 结算版本 + 操作类型”；同一作用域重复执行不得新增流水或改变余额。

### 正确比分盘（Correct Score）契约

正确比分盘是仅在 `ADVANCED` 房间开放的平台虚拟盘（`supplier = PLATFORM`、`supplier_market_id = 2`），与 1X2 盘（`supplier_market_id = 1`）在同一比赛并存。比分盘无外部赔率源，赔率全部为平台固定虚拟规则，必须在展示与规则说明中标注为“平台虚拟积分规则”，不代表真实博彩赔率。

**候选集（17 档）：** 明列 16 个比分——主胜 `1-0 / 2-0 / 2-1 / 3-0 / 3-1 / 3-2`、客胜镜像 `0-1 / 0-2 / 1-2 / 0-3 / 1-3 / 2-3`、平局 `0-0 / 1-1 / 2-2 / 3-3`——加一档 `OTHER` 兜底，代表任何不在明列集合内的最终比分。`outcomes.selection` 存字符串（如 `"2-1"`、`"OTHER"`），1X2 的 `HOME/DRAW/AWAY` 不变。

**平台固定虚拟倍率表（decimal odds，起始值，可后续调整）：**

| 比分 | 倍率 | 比分 | 倍率 |
|---|---:|---|---:|
| `1-1` | 6.0 | `2-2` | 12.0 |
| `1-0` / `0-1` | 7.0 | `3-0` / `0-3` | 15.0 |
| `2-1` / `1-2` | 8.0 | `3-1` / `1-3` | 15.0 |
| `0-0` | 8.0 | `3-2` / `2-3` | 20.0 |
| `2-0` / `0-2` | 9.0 | `3-3` | 28.0 |
| `OTHER` | 5.0 | | |

设计原则：常见比分低倍、罕见与高比分高倍、`OTHER` 兜底最低；数值为平台虚拟规则起始值，可在不改变契约结构的前提下调整。

**门禁与风控：**

- 只有 `ADVANCED` 房间接受比分预测；`STANDARD` 房间由服务端（domain 与 SQL）拒绝比分盘提交，前端隐藏不作为权限边界。
- 单张比分票投入上限沿用全局 20,000，且不超过可用余额；比分票的原子冻结与幂等作用域与 1X2 一致。
- 同一用户在同一房间对同一比赛只能持有一张未结算的比分票；重复提交在服务端拒绝且不冻结积分。
- 房间初始积分维持首次加入一次性 10,000，不因房间档位不同而改变。

**结算判定：** 取 `fixtures.homeScore/awayScore` 为最终比分。所选比分与最终比分完全相等为赢；`OTHER` 在最终比分不属于上表 16 个明列比分时为赢；否则为输。确认取消/无效退还本金，推迟/中断保持冻结待结算，四舍五入、账本追加、幂等与赛果更正冲正重结规则与上方 1X2 结算表完全一致（比分盘无“走盘/PUSH”）。

API-FOOTBALL 官方日配额为 100 次计费请求；系统内部硬上限为 95，剩余 5 次始终作为供应商侧异常缓冲，不纳入业务调度。

- 剩余额度接近保护线时，依次停止滚球展示、停止普通赛前赔率同步，并将无法保持新鲜度的市场标为 `DATA_UNAVAILABLE`；最终赛果、结算和重试保持最高优先级。
- 发布前必须使用真实比赛日数据回放端点数、分页、同时比赛、超时和失败重试；最坏日总请求必须不超过 95，普通同步不得消耗受保护 10 次额度。

## Innovation & Novel Patterns

### Detected Innovation Areas

本产品不以突破性技术为创新点，而是一种克制的交互与机制组合创新：把真实赔率、可调积分投入、封盘后公开和可审计账本组合成朋友之间的足球判断记录。

1. **赔率与积分共同表达判断强度：** 用户不仅选择结果，还通过投入多少积分表达信心，赔率则反映判断难度。
2. **封盘后公开的朋友判断账本：** 赛前隐藏其他人的选择，封盘后统一公开，减少跟随和互相影响，同时增强观赛讨论。
3. **盘口体验与资金链路彻底分离：** 保留赔率、投入、收益计算与复盘价值，但产品不存在真钱、兑换、支付和奖品能力。
4. **可解释排名：** 每次排名变化都能追溯到预测单、赔率快照、积分冻结、结算和补分记录，而不是只显示最终分数。

### Market Context & Competitive Landscape

现有足球预测产品已经验证了比分或胜负预测、私人联赛、自动计分和排行榜的需求。本产品不以赛事数量或大众用户规模竞争，而是填补以下使用空白：

- 普通固定计分游戏不能充分表达判断信心和赔率价值。
- 群聊和表格缺少自动封盘、结算、排名与审计。
- 真钱产品虽然提供赔率和投入机制，但不符合免费朋友娱乐的产品边界。

差异化并非不可复制的技术壁垒，而是面向 3～10 人熟人群体的克制整合：进入快、判断表达充分、赛前互不影响、结果可信且长期房间无需人工维护。

### Validation Approach

世界杯验证轨需要验证以下创新假设：

- 用户能否在 60 秒内理解“赔率 × 积分投入”的基本机制。
- 至少 4 名用户能够正确解释一笔余额变化及其对应赔率。
- 用户是否认为该机制比固定比分计分更能表达判断信心。
- 封盘后公开是否增强讨论，而不是造成困惑或降低参与度。
- 连续参与三场比赛后，用户是否愿意继续在俱乐部赛事中使用同一房间。
- 用户是否明确理解积分不能兑换且与真钱无关。

### Risk Mitigation

| 创新风险 | 回退方案 |
|---|---|
| 赔率与投入组合过于复杂 | 提供 500、1,000、2,000 等快捷投入档位，并显示预计返还积分 |
| 用户仍把界面理解为真钱盘口 | 强化非现金文案，移除现金化术语、图标和视觉表达 |
| 用户只关注余额，不理解判断质量 | 同时展示命中率、预测净收益率和可解释战绩 |
| 隐藏预测降低互动 | 赛前显示已提交人数，但不显示具体选择和投入 |
| 真实赔率数据不稳定 | 暂停对应盘口并保留赛事只读展示；固定积分模式必须经过后续范围变更 |
| 机制容易被复制 | 优势落在小群体体验、可靠结算和长期房间数据，而非宣称技术壁垒 |

## Web App Specific Requirements

### Project-Type Overview

`football-predictor` 采用 mobile-first SPA 与可安装 PWA。验证版重点保证用户通过微信邀请链接进入后，能在手机浏览器完成注册或登录、加入房间、查看赔率、提交预测、查看账本和排行榜。核心业务必须在线执行，PWA 安装不是参与前提。

### Technical Architecture Considerations

- 浏览器只访问产品服务端，不得直接调用 API-FOOTBALL。
- 预测提交、赔率确认、封盘判断、积分冻结和结算全部由服务端完成。
- MVP 使用共享缓存与轮询，不引入 WebSocket。
- 页面回到前台、网络恢复或用户主动刷新时，从产品服务端同步最新状态。
- Service Worker 只缓存应用外壳和只读数据，不得缓存 API Key 或敏感响应。
- 离线状态可以查看最近同步的只读内容，但不得离线提交或排队预测，避免恢复网络时越过封盘。
- 断网、数据过期、同步中和封盘必须显示为不同状态。

### Browser Matrix

| 平台 | 支持范围 | 要求 |
|---|---|---|
| iPhone / iPad | Safari 最近两个主要版本 | 完整核心流程、PWA 安装 |
| Android | Chrome 最近两个主要版本 | 完整核心流程、PWA 安装 |
| 微信内置浏览器 | 当前主流版本 | 加入房间、预测、账本、排行榜可用 |
| macOS | Chrome、Safari 最近两个主要版本 | 完整功能 |
| Windows | Chrome、Edge 最近两个主要版本 | 完整功能 |
| 其他浏览器 | Best effort | 不阻止访问，但不作为发布阻塞项 |

不支持 Internet Explorer。

### Responsive Design

- **320～767px：** 单列布局，底部核心导航，预测确认按钮固定在易触达区域。
- **768～1023px：** 增加赛事信息与预测面板并列空间。
- **1024px 以上：** 主赛事区与房间榜、账户摘要组成双栏布局。
- 所有关键操作必须在不横向滚动的情况下完成。
- 赔率变化、已选结果、投入积分和预计返还必须在同一确认区域清晰展示。
- 必须适配刘海屏、安全区域、动态字体和横竖屏变化。

### Performance Targets

- 移动网络下，第 75 百分位页面体验目标为 `LCP ≤ 2.5s`、`INP ≤ 200ms`、`CLS ≤ 0.1`。
- 从产品服务端缓存读取赛事和排行榜时，API 响应 `p95 ≤ 800ms`。
- 预测提交与积分冻结响应 `p95 ≤ 1s`；结果返回前按钮必须防止重复提交。
- 赔率、赛况展示允许按照免费额度每 5～10 分钟更新。
- 封盘、余额变化和结算完成后，用户下一次同步必须获得一致状态。
- 首屏不得依赖球队 Logo 或非必要大图才能完成渲染。

### SEO Strategy

- 验证版不设 SEO 获客目标。
- 邀请链接、房间、个人战绩、预测单和排行榜必须设置 `noindex`，且不得进入 sitemap。
- 正式版仅允许公开首页、规则说明、帮助页和公开赛事介绍页被索引。
- 私人房间链接不得在社交预览中泄露成员、余额或预测内容。
- SEO 与公开页面不得成为 MVP 发布阻塞项。

### Accessibility Level

以 WCAG 2.2 AA 为目标：

- 不得只用红色和绿色区分赢、输、上涨或下跌。
- 所有图标、盘口状态和结果必须有文字标签。
- 交互元素支持键盘操作，并具有清晰焦点状态。
- 点击目标必须适合移动触控。
- 动态余额、封盘和结算变化提供可被辅助技术识别的状态提示。
- 支持浏览器字体放大至 200%，核心流程不得被遮挡。
- 动效遵循 `prefers-reduced-motion`。
- 表单错误必须说明原因和恢复方式，例如 `MARKET_CLOSED`、`ODDS_CHANGED`、`INSUFFICIENT_POINTS`。

### Implementation Considerations

- 优先保证手机端加入与预测流程，再扩展桌面信息密度。
- 微信内置浏览器必须进入实际测试矩阵。
- 不使用浏览器时间作为封盘依据，客户端倒计时仅供展示。
- 所有写操作带幂等键，页面刷新或网络重试不能产生重复预测。
- PWA 更新不得在用户填写预测时强制刷新。
- 每次正式发布至少验证一台 iPhone、一台 Android 手机和一个桌面浏览器。

## Project Scoping & Phased Development

### MVP Strategy & Philosophy

**MVP Approach：** 问题验证型 MVP

**Release Mode：** 分阶段交付

**核心目标：** 验证朋友群是否愿意持续使用“真实赔率 × 虚拟积分 × 自动账本”，代替群聊和表格。

**Resource Requirements：**

- 1 名全栈开发者，覆盖 PWA、服务端、数据库和定时任务。
- 产品负责人兼验收人员。
- 3～10 名真实测试用户。
- 不建立独立管理后台、不使用 WebSocket、不接入付费服务。

### MVP Feature Set — Phase 1 世界杯验证轨

#### Core User Journeys Supported

1. 普通用户注册、登录并恢复账号。
2. 用户创建私人房间、确认规则并分享邀请链接。
3. 朋友登录后加入房间并获得独立 10,000 初始积分。
4. 查看世界杯比赛、赛前 1X2 赔率并提交积分预测。
5. 系统自动封盘、公开预测、结算积分并更新排行榜。
6. 超级管理员处理账号、违规房间、数据异常和系统状态。

#### Must-Have Capabilities

**身份与权限**

- 用户名和密码注册、登录、退出。
- 普通用户换设备后可以恢复账户数据。
- 注册时生成一次性恢复码，不收集手机号或邮箱。
- 两个超级管理员账号由系统预置，不允许公开注册获得超管权限。
- 普通用户、房主、超级管理员采用明确的服务端权限控制。

**公开与私人房间**

- 普通用户可以创建公开或私人房间并成为房主；私人房间生成邀请链接，公开房间进入大厅。
- 已登录用户可以从大厅加入公开房间，也可以通过邀请链接加入私人房间；世界杯正式验证只要求运行一个目标房间。
- 房间名称、类型标签、成员列表、私人邀请链接重置、规则确认。
- 房主可以查看成员及提交状态，但封盘前不能查看具体选择。
- 不建设独立房主管理后台。

**赛事与预测**

- 一个 bookmaker 的世界杯赛前胜平负。
- 单项预测，单张最高投入 20,000 分且不得超过可用余额。
- 服务端校验赔率版本、数据新鲜度、盘口状态和实际开球时间。
- 封盘前允许提交，不设置人为提前截止。
- 封盘后公开房间成员预测。
- 滚球比分和赔率仅作只读展示。

**积分与账本**

- 每个用户在每个房间拥有独立持久积分账户。
- 首次加入房间获得一次 10,000 分。
- 可用、冻结和已结算积分分开记录。
- 所有变化通过不可变账本流水解释。
- MVP 不包含普通补分、转账、购买、兑换和奖励。

**自动运行**

- 赔率、比分和赛果定时同步。
- 每日 API 请求硬上限 95 次。
- 自动封盘、幂等结算、异常重试和赛果纠正。
- 房间排行榜、预测历史和账本明细。
- 数据异常时暂停预测，不使用过期赔率。

**超级管理员**

- 两个预置超管通过统一登录入口登录。
- 查看用户与房间基本状态。
- 禁用或恢复用户账户。
- 限制、关闭或恢复违规房间。
- 查看 API 配额、同步任务、结算任务和审计记录。
- 触发安全重试，但不能直接覆盖余额或删除账本。
- 超管功能作为 PWA 内的角色页面，不建设第二套后台。

**产品边界**

- 首次注册、创建房间和加入房间时确认年龄与非现金规则。
- 固定页脚声明。
- 举报违规房间。
- 无充值、提现、支付、奖品、现金映射或外部下注链接。

### Phase 2 — 正式产品轨

- 公开排行榜。
- 完整多房间管理与房间切换。
- 私人房间补分申请、`OWNER_GRANT` 与房主审批。
- 所有房间统一采用首次加入一次 10,000 分的独立账户；不使用 `SYSTEM_GRANT`。
- 亚洲让球、大小球。
- 2～8 项串关。
- 数据可靠后开放滚球积分预测。
- 多 bookmaker 市场共识。
- 明确标识的模型赔率。
- 阶段榜、长期战绩和赛后分享卡。
- 正式开放前完成体育数据展示授权检查。

### Phase 3 — Expansion

- 覆盖世界杯后的英超、欧冠及其他足球赛事。
- 用户长期命中率、收益率、擅长盘口和历史荣誉。
- 房间赛季、历史档案和跨赛事统计。
- 在不改变非现金边界的前提下提升数据实时性和赛事覆盖。

### Risk Mitigation Strategy

**Technical Risks**

- 最大风险是赔率同步、封盘竞态和账本一致性。
- 使用服务端权威时间、事务冻结、幂等键、赔率快照和冲正流水控制。
- 免费 API 不可靠时暂停市场，而不是接受旧赔率。

**Market Risks**

- 用户可能只在世界杯期间短期参与。
- 通过连续三场参与率、用户访谈及世界杯后俱乐部赛事延续验证。
- 如果赔率机制理解困难，提供快捷投入和解释性确认界面。

**Resource Risks**

- 若资源不足，优先保留登录、一个目标房间、赛前 1X2、积分账本、自动结算和排行榜。
- 首先取消滚球展示精细化、PWA 安装优化和超管高级筛选，但不取消账本一致性、服务端封盘及非现金边界。
- 不通过增加独立后台、WebSocket 或多数据源扩大 MVP。

## Functional Requirements

### 用户账户与权限

- **FR1:** 普通用户可以使用用户名和密码注册账户，无需提供手机号或邮箱。
- **FR2:** 用户可以登录、退出，并在其他设备登录同一账户。
- **FR3:** 用户注册完成后仅能查看一次恢复码；用户可以使用“用户名 + 有效恢复码 + 新密码”恢复账户，恢复成功后旧恢复码和全部既有会话失效，并仅展示一次新的恢复码。
- **FR4:** 用户可以设置和修改对房间成员展示的昵称。
- **FR5:** 用户注册时必须确认年满 18 岁及当前版本的非现金使用规则；规则版本更新后，用户执行下一次受保护写操作前必须重新确认。
- **FR6:** 系统固定预置两个超级管理员账号，公开注册或产品内操作不能创建第三个超级管理员；超级管理员首次登录必须修改初始密码，凭证重置或账号替换必须通过受控运维流程完成并留痕。
- **FR7:** 系统必须按角色限制操作：普通用户只能操作自己的账户、预测和所属房间数据；房主额外管理其创建房间的邀请、成员状态及 Phase 2 补分；超级管理员只能执行 FR54～FR58，且受 FR59 限制。
- **FR8:** 被禁用账户的既有会话必须失效，且不能创建或加入房间、提交预测、查看私人房间数据或执行其他受保护操作；账户恢复后可以重新登录并访问原有账户、房间和账本数据。

### 公开、私人房间与成员关系

- **FR9:** 已登录普通用户可以创建 `PUBLIC` 或 `PRIVATE` 房间并成为房主；房间类型创建后不可变。
- **FR10:** 创建房间时，房主必须确认当前版本的房间使用规则。
- **FR11:** 房主可以生成和重置房间邀请链接；重置后旧链接立即失效，已加入成员、积分账户、预测和账本记录保持不变。
- **FR12:** 已登录用户确认当前房间规则后可以通过有效邀请链接幂等加入未关闭、未限制的私人房间；重复加入不得重复创建成员关系或发放初始积分。
- **FR13:** 用户可以加入多个公开或私人房间并在房间之间切换；已登录用户可以浏览仅包含 `ACTIVE + PUBLIC` 房间的公开大厅，并在确认规则后按房间 ID 幂等加入，私人房间不得出现在大厅中。
- **FR14:** 用户可以查看房间成员及其房间角色。
- **FR15:** 房主可以查看哪些成员已经提交预测，但封盘前不能查看其具体选择和投入。
- **FR16:** 用户可以举报涉嫌用于真钱活动或其他违规用途的房间。

### 赛事与盘口数据

- **FR17:** 用户可以浏览目标足球赛事、比赛时间和比赛状态。
- **FR18:** 用户可以查看指定 bookmaker 的赛前胜平负赔率、更新时间和数据状态。
- **FR19:** 系统可以根据供应商数据更新改期后的开球时间和比赛状态。
- **FR20:** 用户可以查看滚球比分和滚球赔率；验证阶段这些数据仅供查看。
- **FR21:** 用户可以区分数据正常、同步中、过期、暂停和不可用状态。
- **FR22:** 当供应商剩余额度接近受保护 10 次请求、赔率超过 NFR32 新鲜度或数据无法验证时，系统必须停止相应同步并把受影响盘口标记为 `DATA_UNAVAILABLE`，且不得接受新预测。
- **FR23:** 用户浏览、刷新、切换房间或重复打开比赛只能读取产品缓存，不得直接或同步触发外部供应商请求。
- **FR24（Phase 2）:** 用户可以查看多 bookmaker 市场共识和明确标识的模型赔率，并能区分 `MARKET` 与 `MODEL` 数据。

### 预测提交与公开

- **FR25:** 用户可以选择一个开放结果并填写不超过 20,000 且不超过可用余额的积分投入。
- **FR26:** 用户提交前可以查看选择、确认赔率、投入积分和预计返还。
- **FR27:** 用户可以提交赛前单项预测。
- **FR28:** 系统只在盘口开放、实际开球前且赔率数据有效时接受赛前预测。
- **FR29:** 赔率变化时，系统可以要求用户基于最新赔率重新确认。
- **FR30:** 预测被拒绝时，用户可以看到明确原因和可执行的恢复方式。
- **FR31:** 被拒绝的预测不会生成预测单或改变积分。
- **FR32:** 用户重复点击或请求重试不会产生重复预测和重复积分冻结。
- **FR33:** 用户可以查看自己的预测历史、赔率快照和当前状态。
- **FR34:** 封盘前，其他成员只能看到提交状态；封盘后可以查看成员的选择和投入。
- **FR35（Phase 2）:** 用户可以提交亚洲让球、大小球、2～8 项串关及符合数据条件的滚球预测。

### 积分账户与账本

- **FR36:** 用户在每个房间拥有相互独立的积分账户。
- **FR37:** 用户首次加入每个房间时获得一次 10,000 初始积分。
- **FR38:** 房间积分持续保存且不进行每周自动重置。
- **FR39:** 用户可以区分非负的可用积分、非负的冻结积分、已结算变化及因赛果更正产生的待抵扣 `correction_debt`；只有可用积分可以投入预测。
- **FR40:** 系统接受预测时必须在同一原子操作中扣减可用积分、增加等额冻结积分、创建预测单及其赔率快照并写入冻结流水；任一部分失败时全部不生效。
- **FR41:** 系统必须按 Point & Settlement Contract 处理赢、输、走盘、确认取消、推迟、中断和未最终确认状态，并仅在预测单最终返还值上执行一次四舍五入。
- **FR42:** 用户可以查看每笔冻结、结算、退款、补分、冲正、重新结算和债务抵扣流水，以及其关联预测、房间、结算版本和操作时间。
- **FR43（Phase 2）:** 私人房间成员可以申请补分，房主可以决定补分数量并批准或拒绝。
- **FR44（Phase 2）:** 房间成员可以申请补分，补分记录公开展示且不改变首次加入只发放一次初始积分的规则。
- **FR45（Phase 2）:** 补分记录与预测收益分开显示，且不计入预测净收益和收益排名。
- **FR46:** 用户不能购买、出售、转让、赠送或兑换积分。

### 结算、排名与战绩

- **FR47:** 系统只能在供应商确认最终赛果或确认取消后自动结算；推迟、中断或状态未最终确认的预测必须保持冻结和待结算。
- **FR48:** 系统可以安全重试未完成的冻结、结算、取消退款或更正；以“预测单 + 结算版本 + 操作类型”为幂等作用域，重复执行不得新增流水或改变余额。
- **FR49:** 供应商更正赛果时，系统必须先以新结算版本冲正原结算，再应用新结果并重算排行榜；扣减超过可用积分时，可用积分降至 0，差额进入 `correction_debt`，不得改变其他预测的冻结额。
- **FR50:** 用户可以查看房间排行榜、余额、净收益和已结算预测。
- **FR51:** 用户可以从赔率快照和账本记录解释预测结果及排名变化。
- **FR52（Phase 2）:** 用户可以查看公开排行榜、阶段榜、长期命中率、虚拟收益率和擅长盘口。
- **FR53（Phase 2）:** 用户可以生成不包含敏感房间数据的赛后战绩分享卡。

### 超级管理员与系统运营

- **FR54:** 超级管理员可以查看用户的启用/禁用状态、房间的正常/限制/关闭状态及相关举报，但不能查看密码、恢复码、完整会话令牌或未封盘预测选择。
- **FR55:** 超级管理员可以禁用和恢复普通用户账户。
- **FR56:** 超级管理员可以查看举报并限制、关闭或恢复违规房间。
- **FR57:** 超级管理员可以查看当日供应商计费请求量、各请求池消耗、剩余额度、最后同步时间、数据新鲜度、待结算任务、失败任务和关联审计记录。
- **FR58:** 超级管理员重新确认身份后，可以对失败的同步或结算任务触发使用原幂等作用域的安全重试，但不能修改任务输入、赔率快照或结算结果。
- **FR59:** 超级管理员不能直接覆盖积分余额、删除原始预测或删除账本流水。
- **FR60:** 系统必须审计账户禁用/恢复、房间限制/关闭/恢复、邀请重置、超级管理员凭证重置或替换、安全重试、规则确认、结算更正、数据来源和供应商条款版本；每条记录包含操作者或系统主体、目标、动作、结果、时间和关联审计标识。审计记录可能分布在账户、房间和运营等多个存储中；超级管理员审计视图必须把它们合并为单一按时间排序的可追溯轨迹，且对元数据做密文/令牌/恢复码/邀请明文脱敏（详见 2026-07-15 RBAC 审计报告）。

### 公开大厅与长期产品

- **FR61:** 用户可以进入公开大厅浏览注册用户创建的公开房间；大厅本身不是系统房间，也不持有积分账户。
- **FR62:** 用户确认规则后可以直接加入公开房间；首次加入该房间获得一次独立 10,000 初始积分。
- **FR63（Phase 2）:** 用户可以在不同房间中保留独立余额，同时累积个人长期战绩。
- **FR64（Phase 3）:** 房间可以跨世界杯、俱乐部联赛和其他足球赛事持续存在。

### Web 体验、隐私与产品边界

- **FR65:** 用户可以在受支持的手机和桌面浏览器完成全部核心流程。
- **FR66:** 用户可以将产品安装为 PWA，但未安装时仍可正常参与。
- **FR67:** 断网时用户可以查看最近同步的只读内容，但不能提交或排队预测。
- **FR68:** 页面恢复连接或回到前台时可以同步产品服务端的最新状态。
- **FR69:** 私人房间、预测、账本和排行榜不会被搜索引擎公开索引。
- **FR70:** 用户可以申请删除账户；系统可以解除其公开身份，同时保留维持账本一致性所必需的最小记录。
- **FR71:** 所有页面固定展示简版非现金声明，用户可以查看完整使用规则。
- **FR72:** 产品不提供充值、提现、支付、资金托管、现金映射、奖品兑换或外部下注入口。

### 高级房间与正确比分盘

以下能力交付 Phase 2 高级盘口的首个增量：在 1X2 之外并存提供平台虚拟的正确比分盘，且不改变既有 1X2 预测、赔率、结算与展示行为。规则细节见 Point & Settlement Contract 的“正确比分盘（Correct Score）契约”。

- **FR73:** 用户创建房间时可以选择房间档位 `STANDARD` 或 `ADVANCED`；档位创建后不可变，既有房间默认 `STANDARD`。
- **FR74:** 只有 `ADVANCED` 房间开放正确比分盘；服务端强制该门禁，`STANDARD` 房间用户提交比分预测必须被拒绝，前端隐藏不作为权限边界。
- **FR75:** 在 `ADVANCED` 房间，用户可以对开放比赛从平台比分候选集（16 个明列比分加 `OTHER` 兜底）中选择一个比分，填写不超过 20,000 且不超过可用余额的积分投入，提交前可查看该比分倍率与预计返还。
- **FR76:** 系统按平台固定虚拟倍率表提供比分赔率，明确标注为平台虚拟积分规则；比分盘不依赖外部赔率源，即使同场 1X2 使用真实赔率，比分盘仍保持平台虚拟赔率。
- **FR77:** 同一用户在同一房间对同一比赛只能持有一张未结算的比分票；重复提交必须被服务端拒绝并给出明确原因，且不冻结积分。
- **FR78:** 系统按最终比分完全相等判定比分盘：所选比分与最终比分一致为赢，`OTHER` 在最终比分不属于明列集合时为赢，否则为输；确认取消退款、幂等、账本追加与赛果更正规则与 1X2 一致。
- **FR79:** 1X2 与正确比分盘在同一比赛并存；比分盘为加法能力，赔率版本与 `ODDS_CHANGED` 重新确认、服务端封盘判断、原子冻结等既有约束同样适用于比分盘。

## Non-Functional Requirements

### Performance

- **NFR1:** 移动端第 75 百分位达到 `LCP ≤ 2.5s`、`INP ≤ 200ms`、`CLS ≤ 0.1`。
- **NFR2:** 在 NFR4 负载下，从产品缓存读取赛事、房间和排行榜的服务端响应 `p95 ≤ 800ms`。
- **NFR3:** 在 NFR4 负载下，预测提交、积分冻结及本地已知的数据不可用拒绝响应均须达到 `p95 ≤ 1s`。
- **NFR4:** 系统应支持至少 20 个用户在 10 秒内同时提交预测，且重复单、重复冻结均为 0。
- **NFR5:** 完成结算后，排行榜和用户余额应在 60 秒内对用户可见。

### Reliability & Data Integrity

- **NFR6:** 预测单创建与积分冻结必须同时成功或同时失败。
- **NFR7:** `MARKET_CLOSED`、`ODDS_CHANGED`、`DATA_UNAVAILABLE` 等拒绝结果造成的积分变化必须为 0。
- **NFR8:** 已向用户确认成功的预测，在应用进程重启后不得丢失。
- **NFR9:** 供应商最终赛果确认后，预测最终结算成功率必须达到 100%；失败任务必须保持待处理状态并可安全重试。
- **NFR10:** 任何任务重复执行不得造成重复冻结、重复结算或重复补分。
- **NFR11:** 赛果更正不得覆盖原历史，冲正前后的余额差异必须能由账本完整解释。
- **NFR12:** 账户、预测和账本数据至少每 6 小时自动备份一次，备份保留不少于 7 天，灾难恢复目标 `RTO ≤ 4h`、`RPO ≤ 6h`。
- **NFR13:** 在目标比赛开球前 2 小时至赛后 30 分钟期间，按 1 分钟探测统计，核心登录、预测和查账功能可用性目标为 99%。

### Security & Privacy

- **NFR14:** 所有网络传输必须使用 HTTPS，禁止通过明文协议发送凭证、恢复码或会话信息。
- **NFR15:** 密码不得以明文、可逆密文或通用快速哈希保存；密码存储方案及其参数必须通过 NFR21 的适用控制检查，并保留发布版本对应的安全评审记录。
- **NFR16:** 密码、恢复码、API Key 和会话令牌不得写入应用日志或发送到浏览器分析工具。
- **NFR17:** 登录和恢复码验证必须分别按账户与请求来源限流；任一维度在 15 分钟内连续失败 5 次后，后续尝试至少延迟至该窗口结束并记录安全事件；限流窗口到期后自动恢复，不得形成永久账户锁定。
- **NFR18:** 超级管理员会话空闲 30 分钟后失效；执行 FR55 账户禁用/恢复、FR56 房间限制/关闭/恢复、FR58 任务重试及超级管理员凭证重置或替换前必须重新确认身份，确认结果最多有效 5 分钟。
- **NFR19:** 普通用户无法访问其他房间的私人预测、账本或成员数据；房主权限只在其拥有的房间内有效。
- **NFR20:** API-FOOTBALL Key 和数据库管理凭证只能存在于服务端受控环境。
- **NFR21:** 发布前应满足 OWASP ASVS 5.0 Level 1 的适用基础控制，并且不存在未处理的 Critical 或 High 级漏洞。
- **NFR22:** 用户账号删除申请应在 7 天内完成公开身份解除；保留的最小账本记录必须匿名化。
- **NFR23:** 管理、结算、更正和规则确认审计记录至少保留 180 天。

### Accessibility

- **NFR24:** 核心用户流程以 WCAG 2.2 AA 为验收目标。
- **NFR25:** 所有核心操作必须可通过键盘完成，并具有可见焦点。
- **NFR26:** 输赢、盘口变化和状态不得仅依赖红绿颜色表达。
- **NFR27:** 页面字体放大至 200% 时，登录、加入房间、预测确认和查账流程仍可完成。
- **NFR28:** 动态余额、封盘、错误和结算状态必须提供可被辅助技术识别的文字信息。
- **NFR29:** 发布前至少完成自动化无障碍扫描及一次键盘、屏幕阅读器人工检查。

### External Data Integration

- **NFR30:** API-FOOTBALL 每个 `00:00 UTC` 计费日的请求总数不得超过 95；基准预算为静态 5、赛前赔率 10、滚球展示 70、最终赛果/结算/重试 10，其中最后 10 次为普通同步不可使用的最低保护额，官方配额剩余 5 次不得纳入业务调度。
- **NFR31:** 每次计费调用后，本地计数必须与供应商剩余额度响应头校验并采用更保守值；系统至少每日及发生不一致时使用不计费 `/status` 校准 `current` 与 `limit_day`，校准不得提高 95 次内部硬上限。
- **NFR32:** 目标比赛开放预测时，赛前赔率快照新鲜度不得超过 10 分钟；超过阈值立即停止接受新预测。
- **NFR33:** 存在活跃目标比赛且滚球预算充足时，滚球比分和赔率展示更新周期为 5～10 分钟；接近受保护额度时允许延长或停止更新，并明确显示最后更新时间，不宣称秒级实时。
- **NFR34:** 供应商异常、超时、额度不足或赔率超过 NFR32 阈值时，系统必须在检测后 10 分钟内且在下一次接受预测前，将受影响盘口标记为 `DATA_UNAVAILABLE`。
- **NFR35:** 用户页面请求触发供应商调用的数量必须为 0；外部请求失败时，所有用户读取继续命中产品缓存或获得明确不可用响应，不得回源绕过缓存。
- **NFR36:** 每个预测快照必须能够追溯到供应商、bookmaker、比赛、盘口、选择及数据时间。

### Operability & Auditability

- **NFR37:** 每次预测、冻结、结算、冲正和管理操作必须具有可关联的审计标识。
- **NFR38:** 超级管理员可以在 5 分钟内看到关键同步或结算任务失败状态。
- **NFR39:** 系统健康状态必须显示当日供应商请求量、剩余预算、最后同步时间、待结算任务和失败任务。
- **NFR40:** 内部时间判断统一使用可靠的服务器时间；用户本地时间仅用于展示。
- **NFR41:** 日志中不得记录完整恢复码、密码、会话令牌或可直接使用的邀请凭证。
- **NFR42:** 每个阶段发布前必须完成封盘竞态、重复提交、赢/输/走盘/取消/推迟、重复结算、赛果更正、`correction_debt` 抵扣、备份恢复及最坏比赛日 API 预算回放；通过标准为重复账务 0、无法解释账目差异 0、普通同步消耗保护额度 0、日请求不超过 95、备份恢复满足 NFR12，并保存验收证据至少 180 天。
