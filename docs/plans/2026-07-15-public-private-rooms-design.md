# 公开与私人房间设计

## 目标

所有已注册用户都可以创建公开或私人房间。公开房间展示在大厅中，其他已登录用户无需邀请即可加入；私人房间继续使用不可枚举的邀请链接加入。

## 权限模型

- 房间新增不可变的 `PUBLIC` / `PRIVATE` 可见性属性。
- `ACTIVE + PUBLIC` 房间可以在公开大厅中被已登录用户发现和加入。
- `PRIVATE` 房间不进入公开列表，只能通过当前有效邀请加入。
- `RESTRICTED` 或 `CLOSED` 房间不得被新成员加入，也不进入公开大厅。
- 未加入公开房间的用户只能看到房间名、房主昵称和成员数量；成员、积分、账本和预测仍受成员权限保护。

## 创建与加入

- 创建表单要求用户明确选择公开或私人，默认私人，避免意外公开。
- 创建者成为房主，并获得该房间独立的 10,000 初始积分。
- 公开房间通过房间 ID 加入，私人房间通过邀请 token 加入。
- 两条加入路径复用同一原子成员创建与初始积分发放逻辑，重复加入幂等且不重复发分。
- 公开房间不生成或展示邀请 token；数据库允许其邀请摘要为空。私人房间保留当前邀请重置能力。

## 接口与页面

- `GET /api/v1/rooms/public`：列出可加入的公开房间。
- `POST /api/v1/rooms/:roomId/join`：确认规则后加入公开房间。
- `POST /api/v1/rooms`：新增 `visibility` 字段。
- 房间页分成“我的房间”“公开大厅”“创建房间”三个区域。
- 房间卡片标记公开/私人；只有私人房间房主看到邀请管理。

## 数据与兼容

- 新增 PostgreSQL enum `room_visibility` 和 `room.rooms.visibility`，默认 `PRIVATE`，保证现有房间保持私人。
- API 返回房间可见性，前端据此渲染标签和操作。
- PRD 中原“单一系统公开大厅、Phase 2”口径调整为“用户创建公开房间、注册用户直接加入”；公开和私人房间继续使用隔离的房间积分账户。

## 验证

- 数据迁移测试覆盖默认私人和 enum。
- Domain 测试覆盖两类创建、公开加入、私人拒绝公开加入、规则确认和幂等。
- Repository/API 测试覆盖公开列表的数据最小化和加入权限。
- 前端 flow 测试覆盖创建 payload、公开列表加入和私人邀请路径不回归。
