# 房间投入记录与分阶段可见性设计

## 背景

房间详情当前展示成员、余额和比赛，但没有展示本房间的预测投入记录。系统已经持久化预测单、投入积分、确认倍率、结算结果和账本流水，也已有按房间读取预测历史的接口；缺口在于房间详情没有统一呈现这些记录，也没有按比赛阶段和管理角色配置其他成员记录可见性的机制。

本功能只改变记录的读取与展示权限，不改变预测提交、积分冻结、结算或账本写入规则。

## 目标

1. 房间详情展示本房间的投入与判断记录。
2. 当前用户自己的记录始终完整可见。
3. 平台超级管理员按房间控制“未开赛投入可见”。
4. 房主按房间控制“开赛后完整记录可见”。
5. 所有其他成员数据必须由服务端按权限脱敏，不能只依赖前端隐藏。
6. 所有设置修改写入审计日志。

## 非目标

- 不允许房主控制未开赛投入可见性。
- 不允许普通成员修改任何可见性设置。
- 未开赛阶段即使超管开启，也不公开其他成员的具体选择或确认倍率。
- 不修改预测封盘、结算、积分倍率或账本算法。
- 不提供按成员批量导出记录。

## 数据模型

在 `room.rooms` 增加两个布尔字段：

- `pre_match_stake_visible boolean NOT NULL DEFAULT false`
  - 含义：比赛未开赛时，房间成员是否能看到其他成员的投入积分和提交时间。
  - 修改权限：仅平台超级管理员。
- `post_match_ticket_visible boolean NOT NULL DEFAULT true`
  - 含义：比赛实际开赛后，房间成员是否能看到其他成员的完整预测记录。
  - 修改权限：仅房主。

新增 migration，并保持现有房间自动获得上述默认值。设置只是读取策略；预测单和账本记录始终正常持久化。

## 服务端可见性规则

服务端以当前时间与 `kickoff_at` 比较判断比赛阶段，并结合当前用户、房间设置和成员身份生成响应。

### 当前用户自己的记录

无论比赛阶段或开关状态，始终返回：

- 选择
- 投入积分
- 确认倍率
- 提交时间
- 状态
- 预计或最终返还
- 净积分变化
- 结算版本及允许公开的审计引用

### 其他成员的未开赛记录

- `pre_match_stake_visible = false`：只返回成员显示名、是否已提交、预测单状态；隐藏选择、投入、倍率和预计返还。
- `pre_match_stake_visible = true`：额外返回投入积分和提交时间；仍隐藏选择、确认倍率和预计返还。

### 其他成员的开赛后记录

- `post_match_ticket_visible = false`：只返回成员显示名、是否已提交和状态；隐藏选择、投入、倍率、返还及净变化。
- `post_match_ticket_visible = true`：返回选择、投入、确认倍率、提交时间、结算状态、返还和净积分变化。

两个开关分别只作用于对应比赛阶段。如果超管开启未开赛可见，但房主关闭开赛后可见，比赛开赛后其他成员的投入会重新按开赛后规则隐藏。这一行为是两个独立管理权限的直接结果，界面文案必须明确说明。

## 权限与接口

### 读取房间详情

房间详情响应增加只读设置：

```ts
{
  preMatchStakeVisible: boolean;
  postMatchTicketVisible: boolean;
  canManagePreMatchVisibility: boolean;
  canManagePostMatchVisibility: boolean;
}
```

`canManagePreMatchVisibility` 仅超级管理员为 `true`；`canManagePostMatchVisibility` 仅房主为 `true`。

### 超级管理员接口

新增或扩展房间治理接口，用于修改：

```json
{ "preMatchStakeVisible": true }
```

要求当前身份为超级管理员。成功后追加 `ops.audit_events`，记录操作者、房间、旧值、新值、时间和关联 ID。普通用户和房主调用必须返回 403。

### 房主接口

新增房间设置接口，用于修改：

```json
{ "postMatchTicketVisible": false }
```

要求当前用户是该房间房主，且房间存在。成功后追加房间审计记录。普通成员、其他房间房主和超级管理员在未作为该房间房主时不能通过此接口修改。

### 预测历史接口

沿用按房间读取预测历史的接口，但可见字段必须由服务端统一生成。前端收到的数据即为最终可展示范围，不能收到被隐藏字段的原始值。

## 界面设计

### 房间详情

在比赛列表下方增加“投入与判断记录”区域：

- 筛选：“全部成员”“只看我的”
- 汇总：全部、待结算、已结算
- 每条记录显示成员、比赛、阶段、状态以及服务端允许公开的字段
- 被隐藏字段使用“未公开”，并说明由房间可见性规则控制
- 自己的记录不受筛选开关影响，始终完整显示
- 空状态说明提交预测后记录会立即写入

房主可在该区域看到“开赛后记录可见”开关及当前状态。切换前显示明确说明；请求成功后更新，失败时保持原状态并展示错误。

### 超级管理员房间治理

在每个房间治理详情中增加“未开赛投入可见”开关：

- 默认关闭
- 文案明确：开启后只公开投入积分和提交时间，不公开具体选择和倍率
- 显示最近修改时间和操作者（有审计记录时）
- 修改失败不改变界面状态

### 普通成员

能看到两个设置的当前状态说明，但没有修改控件。

## 数据流

1. 用户进入房间详情。
2. 前端并行读取房间详情、余额、成员、比赛和按房间预测历史。
3. 服务端验证会话及房间成员关系。
4. 服务端读取两个可见性字段，并逐条按当前用户与比赛阶段构造脱敏后的预测记录。
5. 前端仅负责展示返回结果和本地筛选，不再次推断敏感字段权限。
6. 超管或房主修改设置时，服务端在同一事务内更新房间字段并追加审计记录。
7. 修改成功后前端重新读取记录，确保展示与服务端策略一致。

## 错误处理

- 未登录：401，并保留安全返回路径。
- 非房间成员读取：403 或 404，遵循现有防枚举约定。
- 非授权角色修改：403，不写设置、不写审计成功事件。
- 房间不存在：404。
- 数据库更新或审计写入失败：事务回滚，设置保持原值。
- 历史读取失败：房间其他区域继续显示，记录区域展示独立错误和重试按钮。
- 记录字段缺失：显示“—”或“未公开”，不得前端猜测。

## 测试策略

### 数据库与领域层

- migration 默认值正确。
- 已有房间应用默认值后保持兼容。
- 超管设置更新与审计在同一事务完成。
- 房主设置更新仅允许目标房间房主。

### API

- 本人的未开赛和已开赛记录始终完整。
- 未开赛开关关闭时，其他成员投入、选择和倍率均不返回。
- 未开赛开关开启时，只返回其他成员投入和提交时间，不返回选择与倍率。
- 开赛后开关关闭时，其他成员完整字段不返回。
- 开赛后开关开启时，返回其他成员完整允许字段。
- 超管、房主、普通成员的修改权限分别正确。
- 更新失败时没有部分设置或孤立审计记录。

### 前端

- 房间详情能展示投入记录、汇总和筛选。
- 隐藏字段显示“未公开”。
- 超管页面只展示超管开关。
- 房主页面只展示开赛后开关。
- 普通成员没有修改控件。
- 保存失败时开关回到服务端原值并显示错误。

## 上线与兼容性

1. 先执行 migration，使所有房间获得安全默认值。
2. 部署服务端权限与脱敏逻辑。
3. 部署房间详情和管理界面。
4. 运行权限、类型、构建和目标测试。
5. 线上验证默认关闭未开赛投入、默认开启开赛后完整记录，并验证未授权请求返回 403。

旧客户端不读取新字段时仍可正常使用现有房间、预测和账本功能。
